## 0. 为什么这是硬骨头

当前回测的 60% CAGR、Sharpe 1.9 全部建立在一个不可信的地基上：

| 问题 | 现状 | 后果 |
|------|------|------|
| P0-1 前视偏差 | `evaluator_fixed.py:383` `score_map = dict(FIXED_SCORE_MAP)` 全程固定评分 | 回测到 2024 年，却用了 2026 年才知道的评分 |
| P0-2 幸存者偏差 | `FIXED_UNIVERSE` 19 只全是当下龙头，无退市/剔除股 | 等权持有 +34.77% vs 大盘 −2.3%，超额全部来自"选对池子" |

这两项不是"改几行"能解决，需要**数据层 + 引擎层**的协同改造。

## 1. P0-1 时点评分（point-in-time）设计

### 1.1 现状与目标

- **现状**：`run_backtest`（evaluator_fixed.py）全程用 `FIXED_SCORE_MAP` 固定评分，`decide_fn` 按评分排序选股。
- **目标**：回测到 T 日，用**截至 T 日能拿到的数据**实时算分（复用 `FactorEngine.score_batch` 的能力）。

### 1.2 数据可用性盘点（关键约束）

| 数据类型 | 历史可用 | 依据 |
|---------|:---:|------|
| 日线价格（收盘/开盘） | ✅ | `data_router.get_history` 可拉任意历史 |
| 技术指标（MA/动量/RSI/MACD） | ✅ | 从历史日线截取到 T 日即可算 |
| 财务指标（ROE/增速/毛利） | ⚠️ 部分 | `get_financial_history`（data_layer.py:440）有 8 季度历史，**但无报告发布日期（ann_date）** |
| 截面数据（T 日全池因子） | ⚠️ 需构造 | 截面标准化需 T 日所有标的的因子值 |

**核心难点 = point-in-time 财务**：回测到 2024-03，只能用 2024-03 之前**已发布**的财报（如 2023Q3），不能用 2024-04 才发布的 2023 年报。当前 `get_financial_report` 返回的是**当前最新**财报（2026 年的），直接用于回测就是前视。

### 1.3 三个方案（按实施成本递增）

**方案 A（最小可用，先做）——报告期滞后近似**
- `get_financial_history` 已有多季度财务，按"报告期 + 发布滞后"过滤：季报滞后 45 天、年报滞后 90 天。
- 回测到 T 日，只用 `报告期截止日 + 滞后天数 <= T 日` 的财报。
- **消除最严重的未来函数**（用未来财报回测过去），但不精确（滞后天数是近似）。

**方案 B（完整）——接入报告发布日期（ann_date）**
- 蜻蜓 CSC / baostock 的财报接口有 `ann_date`（公告日期）。
- 存储"财报 + ann_date"快照；回测到 T 日只用 `ann_date <= T` 的财报。
- 精确 point-in-time，但需改造 `get_financial_history` 返回 ann_date。

**方案 C（终极）——每日因子快照**
- `run_factor_daily.py` 每天落盘 `factor_scores_{date}.json`（含全池因子 + 评分）。
- 回测直接读历史快照（回测到 T 日读 T 日快照）。
- 最精确、最快（回测不再实时算），但**需从今天起积累历史**，短期无法回测更早的历史。

### 1.4 推荐路线

```
第一阶段：方案 A（报告期滞后）→ 立即消除前视，回测数字第一次"可信"
第二阶段：方案 B（ann_date）→ 精确 point-in-time
第三阶段：方案 C（快照积累）→ 长期最优，回测提速
```

**引擎改造点**（方案 A/B 共用）：
1. `FactorEngine.score_batch` 增加 `as_of_date` 参数，所有数据拉取按 `as_of` 截断。
2. `run_backtest` 的 `score_map = dict(FIXED_SCORE_MAP)` 改为：每个 `day_idx` 用 `as_of=date_list[day_idx]` 调用 `score_batch` 重算评分。
3. 性能优化：逐日重算慢（19 只 × N 天），先按周/月降频重算，或用缓存。

## 2. P0-2 幸存者偏差设计

### 2.1 现状与目标

- **现状**：`FIXED_UNIVERSE` 是 19 只"现在还在关注"的龙头（半导体/AI算力/新能源），无历史剔除/退市标的。
- **目标**：回测股票池包含"历史某时点入选、后来剔除/退市"的标的，反映真实可投资集合。

### 2.2 数据源分析

| 数据源 | 可得性 | 说明 |
|--------|:---:|------|
| baostock 退市股名单 | ✅ | `query_stock_basic` + 退市状态，可得 A 股历史退市列表 |
| 历史 WATCHLIST 快照 | ⚠️ | 若维护了"每次变更存档"，可直接用；当前未维护 |
| 宽基指数历史成分 | ✅ | 沪深300/中证500 历史成分（蜻蜓CSC/baostock 可查） |
| 蜻蜓 CSC 历史成分 | 待确认 | 券商数据源可能有历史成分股 |

### 2.3 三个方案

**方案 A（补退市股）**：用 baostock 拉 A 股历史退市股名单，加入回测股票池。消除"只留活着的龙头"的偏差。

**方案 B（历史候选池快照）**：从今天起，每次 WATCHLIST/票池变更时存档 `universe_{date}.json`，回测用历史快照。

**方案 C（宽基指数成分）**：用沪深300 + 中证500 历史成分作为回测股票池，彻底消除"手工精选"的幸存者偏差，回测结果反映"在全市场里选股"的真实难度。

### 2.4 推荐路线

```
第一阶段：方案 A（baostock 退市股）→ 快速补齐"被剔除/退市"的盲区
第二阶段：方案 C（宽基成分）→ 回测反映真实可投资域，数字最可信
第三阶段：方案 B（快照）→ 长期维护成本最低
```

## 3. 实施建议与验收标准

### 3.1 分批实施

| batch | 内容 | 预期效果 |
|-------|------|---------|
| 1 | 方案 A 报告期滞后 + 引擎 `as_of` 改造 | 回测数字第一次消除前视，CAGR 大概率大幅下降 |
| 2 | 方案 A 退市股补池 | 消除幸存者偏差，进一步压低收益 |
| 3 | 方案 B/C 精化 | point-in-time 精确 + 快照提速 |

### 3.2 验收标准（How we know it's done）

1. **回测可复现**：同参数重跑两次，结果一致（时点评分确定性）。
2. **前视消除**：`run_backtest` 里不再有 `FIXED_SCORE_MAP` 固定评分；回测到 T 日的评分只依赖 T 日及之前的数据。
3. **幸存者消除**：回测股票池含历史退市/剔除标的；等权持有回测池的超额收益应显著低于当前 +34.77%。
4. **数字可信后**：摘除 dashboard 回测 Tab 顶部的红色告警条（那是临时止血，不是终点）。

### 3.3 风险提示

- **时点评分会让回测收益大幅下降**（可能从 +60% 降到个位数甚至负），这是**正确方向**——真实策略能力就是如此，不能因为"数字变难看"就回退。
- 方案 A 的"报告期滞后 45/90 天"是近似值，需用真实财报发布节奏校准。
- 逐日重算评分的性能需要缓存（19 只 × 1000 天 × 数据拉取会很慢）。

---

## 4. 一句话总结

**P0-1/P0-2 是"让回测从玩具变成工具"的最后一道坎。** 核心动作是：① 回测引擎从"固定评分"改为"逐日 as-of 评分"（财务用报告期滞后近似 point-in-time）；② 股票池从"19 只龙头"改为"含退市股/宽基成分"。做完这两步，60% CAGR 会回归到真实水平，dashboard 才能真正对外宣称回测数字。
