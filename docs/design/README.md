# 生产化设计方案总览

> **状态**: 设计阶段 | **目标**: 将 Hermes 从原型级提升到生产级
>
> 本文档是基于 2026-07-03 深度评审产出的 8 个维度设计方案的索引和路线图。

---

## 背景

系统经过一年的迭代，业务逻辑已趋于成熟——三策略体系完整，回测方法论规范，LDS 双门风控设计合理。但工程化严重不足：

- 🔴 零测试覆盖，硬编码凭据，无 CI/CD
- 🟡 双引擎评分不一致，超大文件，配置重复
- 🟢 Dashboard 功能齐全但实现简陋

## 总体路线图

```
Phase 0 (立即 - 本周)
├── 1. 安全加固：移除硬编码凭据，创建 .env.example
├── 2. 工程化基础：添加 pyproject.toml, ruff 配置
└── 3. 数据管线：原子文件写入改造

Phase 1 (本月)
├── 4. 测试基础设施：核心路径单元测试 + 回测回归测试
├── 5. 工程化基础：CI/CD Pipeline (GitHub Actions)
├── 6. 数据管线：缓存管理 + 错误处理标准化
└── 7. 架构拆分：config.py 拆分 + report_v6.py 拆分

Phase 2 (下月)
├── 8. 因子引擎统一：v4.0 接入日报 Pipeline
├── 9. 可观测性：结构化日志 + /health 端点 + Cron 监控
├── 10. 架构拆分：backtest.py / news_engine.py 拆分
└── 11. Dashboard 重构：前端分离 + 数据导出

Phase 3 (持续)
├── 12. 测试覆盖率提升至 80%+
├── 13. Dashboard 交互增强（筛选/下钻/告警配置）
└── 14. 性能优化（大规模回测并行化）
```

## 设计原则

1. **向后兼容**：所有改动保持现有 API 和数据格式不变，通过适配层过渡
2. **渐进式**：每步改动独立可回滚，不追求一次性大重构
3. **假设单人力**：不引入需要团队协作才能维护的复杂工具链
4. **数据安全优先**：涉及金融数据的改动必须经过充分验证
