# 面基投资系统 · 开发工作流 v3（三合一）

> **版本**: v2026.07.03 | 代替 v2
> **核心理念**: OpenSpec 读代码 → grill-me 问需求 → Trellis 拆任务 → TDD 执行

---

## 一、为什么是 v3

v2 引入了「用户只做选择题」的 grill-me 模式，是对的，但还不够。文章说透了：

> Superpowers 方法论没错——**brainstorm → plan → implement 流程本身没问题**。但包装太重了：模块越来越多、文档越来越长、审查越来越累。

v3 的核心认识：**不是去掉规划，而是让三段轮流上场，各干各的事**。

| 阶段 | 谁负责 | 你的角色 | 脑力 | 产出 |
|------|--------|---------|------|------|
| **OpenSpec 探索** | Agent 读代码 → 找缺口 → 问问题 | 回答方向性问题 | 🟢 低 | 一份精简 Spec |
| **grill-me 澄清** | Agent 逐项追问（带建议） | 做选择题（A/B） | 🟢 极低 | 共识（无文档） |
| **Trellis 执行** | Agent 拆纵向切片 → TDD → commit | 审核拆分（可选） | 🟢 低 | 可运行的代码 |

**核心指标**：首遍精度从 ~50% → ~85-90%。

---

## 二、完整工作流

### Phase 1: OpenSpec /opsx:explore — 读代码 + 问方向

不是我凭空写 Spec，而是：

```
Agent 先读代码库
  → 发现当前架构、已有的模式、缺失的部分
  → 提出 2-3 个方向性问题（不是细节）
  → 你回答
  → Agent 写一份精简 Spec（不超过半页）
```

输出：飞书决策记录（标题 + 背景2行 + 选项 + 决策）

### Phase 2: grill-me — 逐项追问，你做选择题

Spec 确定大方向后，grill-me 处理**设计细节**：

```
Agent: "关于这个功能，我还有几个点要确认——"
Q1: "这个模块是独立服务还是现有模块的扩展？
    我建议扩展现有模块，因为结构类似。
    你要独立还是扩展？"
→ 你：扩展

Q2: "认证模型是继承父级还是自建？
    我在 src/services/billing.ts 找到类似模式。
    沿用那个模式？"
→ 你：是

Q3: "验收标准——最基本的端到端路径是什么？
    我猜：用户提交表单 → 保存到 db → 显示成功。
    对吗？"
→ 你：对，再加一个错误处理
```

每个问题 5-10 秒回答。整个 grill-me 约 10-15 分钟。结束时 Agent 对你要的东西比任何文档都清楚。

### Phase 3: Trellis — 纵向切片任务树

grill-me 共识后，不直接写代码，先拆任务。

**关键原则：曳光弹式纵向切片（tracer-bullet vertical slices）**

```
✅ 正确的拆法：
  Issue 1: 用户可以端到端创建最小版本的数据
  Issue 2: 用户可以端到端编辑一个字段
  Issue 3: 用户可以端到端看到第一个校验错误

❌ 错误的拆法：
  Issue 1: 建数据库表
  Issue 2: 写 API
  Issue 3: 写 UI
```

每个切片：
- **AFK**（Agent 可以无人值守）或 **HITL**（需要你参与）
- 优先拆成 AFK
- 有明确验收标准

拆分结果你必须审核通过才执行。

### Phase 4: TDD 执行

每个 vertical slice 按 TDD：

```
写测试（验证行为，不是实现细节）
→ 确认失败
→ 最小实现
→ 确认通过
→ commit
```

遇到复杂问题 → `/diagnose`（先建确定性 pass/fail 信号，不猜 bug）

### Phase 5: 事后补文档

```
代码完成后 Agent 自动：
  → 生成/更新 docs/ 对应 MD
  → 更新 README 链接
  → 打 tag 锁版本
```

**文档不阻塞开发**。

## 三、工具映射

| 原工具 | Hermes Agent 对应 | 用途 |
|--------|-------------------|------|
| `/grill-with-docs` | `session_search` + 我读代码后提问 | 读代码库 + 问问题 |
| `grill-me` | 我直接问选择题（带建议） | 逐项澄清需求 |
| `to-prd` | `write_file` 写飞书决策记录 | 固化共识 |
| `to-issues` | `todo` + 拆 vertical slices | 拆可执行任务 |
| `tdd` | `test-driven-development` skill | 测试优先开发 |
| `diagnose` | `systematic-debugging` skill | 复杂 bug 修复 |
| `trellis mem` | `session_search` | 跨会话上下文 |
| `handoff` | 上下文摘要 | 换 agent/跨会话 |

## 四、飞书决策记录格式（极简版）

```
标题: [功能名] · 决策记录

背景（1-2行）
选项（每行一个，不超过3个）
  A. 方案A — 一句话
  B. 方案B — 一句话
决策 → 选 A
执行计划（不超过3个 vertical slice）
```

你唯一需要做的：**在选项前打勾**，然后说"开干"。
